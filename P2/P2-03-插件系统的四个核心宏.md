# P2-03 插件系统的四个核心宏

> 本文基于 **Qt 6.8.3** 源码。定位：P1-06 的深挖篇——主线讲了四个宏"怎么用
> 各司其职"，本篇把每个宏展开，看它到底生成了什么，以及它们如何串成
> "qobject_cast 为什么安全"的完整链路。

## 1. 四个宏的分工回顾

```
  Q_DECLARE_INTERFACE  接口侧：把接口类与唯一 IID 字符串关联，
                       特化 qobject_cast<接口*>()

  Q_INTERFACES         插件侧：声明插件类实现了哪些接口，
                       moc 据此生成 qt_metacast() 匹配代码

  Q_PLUGIN_METADATA    插件侧：声明插件元数据（IID、JSON 文件），
                       供 QPluginLoader::metaData() 读取

  QT_MOC_EXPORT_PLUGIN moc 产物：生成两个 dll 导出函数
                       （qt_plugin_instance / query_metadata）
```

一句话主线：**接口侧注册 IID，插件侧声明实现和元数据，moc 生成胶水代码，运行时靠 IID 字符串匹配完成类型转换**。下面逐个展开验证这句话。

## 2. Q_DECLARE_INTERFACE：特化 qobject_cast

宏展开后是一组模板特化（`qglobal.h`）：

```cpp
#define Q_DECLARE_INTERFACE(IFace, IId) \
    template <> inline const char *qobject_interface_iid<IFace *>() \
    { return IId; } \
    template <> inline IFace *qobject_cast<IFace *>(QObject *object) \
    { return reinterpret_cast<IFace *>((object ? object->qt_metacast(IId) : nullptr)); } \
    template <> inline IFace *qobject_cast<IFace *>(const QObject *object) \
    { return reinterpret_cast<IFace *>((object ? const_cast<QObject *>(object)->qt_metacast(IId) : nullptr)); }
```

读法：**这个宏本身不做任何注册动作**，它只是告诉编译器"对 IFace 这个类型，`qobject_cast` 的特化版本是调 `object->qt_metacast(IId)` 再强转"。真正的匹配发生在 `qt_metacast()` 里——那是 moc 在插件类上生成的（见 §4）。同时它特化了 `qobject_interface_iid<IFace*>()`，让框架在别处（如 qmlRegisterType 场景）也能反查接口的 IID。

注意末尾的 `#ifndef Q_MOC_RUN` 保护：moc 处理头文件时跳过这段——因为模板特化是给编译器看的，moc 只关心宏标注本身。

## 3. Q_PLUGIN_METADATA 与 Q_INTERFACES：纯标注

这两个宏展开后几乎是"空"的：

```cpp
#define Q_PLUGIN_METADATA(x) QT_ANNOTATE_CLASS(qt_plugin_metadata, x)
#define Q_INTERFACES(x)      QT_ANNOTATE_CLASS(qt_interfaces, x)
```

`QT_ANNOTATE_CLASS` 是一个 moc 可识别的类标注。**它们不产生任何运行时代码**，作用只是给 moc 打标记：

- `Q_PLUGIN_METADATA(IID ... FILE ...)`：moc 把 IID 和 JSON 文件内容记录下来，编进插件二进制的元数据段（`qt_pluginMetaData`），供 `QPluginLoader::metaData()` 在不创建实例的情况下读取；
- `Q_INTERFACES(EchoInterface)`：moc 据此在生成的 `qt_metacast()` 里追加该接口的匹配分支（§4 可见）。

这就是"声明式"宏的典型形态：**信息由 moc 在编译期收集，代码由 moc 在编译期生成**——与 Q_OBJECT / Q_PROPERTY 的元对象机制（P1-01）是同一套思路。

## 4. moc 生成的转换代码：qt_metacast

moc 处理插件类后，生成的类型转换函数长这样（以 P1-06 的 EchoPlugin 为例）：

```cpp
void *EchoPlugin::qt_metacast(const char *_clname)
{
    if (!_clname) return nullptr;
    if (!strcmp(_clname, qt_meta_stringdata_EchoPlugin.stringdata0))
        return static_cast<void*>(this);
    if (!strcmp(_clname, "EchoInterface"))
        return static_cast< EchoInterface*>(this);
    if (!strcmp(_clname, "org.qt-project.Qt.Examples.EchoInterface"))
        return static_cast< EchoInterface*>(this);
    return QObject::qt_metacast(_clname);
}
```

真相大白：`qt_metacast()` 就是把传入字符串（类名或 IID）**逐一 strcmp 比对**，匹配上就把 `this` 修正到对应接口的地址返回。注意第三个分支——比对的正是接口文件里 `Q_DECLARE_INTERFACE` 注册的那个 IID 常量。

这也解释了 P1-06 的铁律：**Q_PLUGIN_METADATA 的 IID 与 Q_DECLARE_INTERFACE 的 IID 必须一字不差**——一个写进 `qobject_cast` 特化（查询方），一个写进 `qt_metacast` 分支（应答方），两端字符串对不上，匹配就落空返回 nullptr。

## 5. QT_MOC_EXPORT_PLUGIN：两个 C 导出函数

moc 在生成文件末尾用这个宏产出插件对外的"门面"——两个固定名字的 C 导出函数：

```cpp
#define Q_PLUGIN_INSTANCE(IMPLEMENTATION) \
        { \
            static QT_PREPEND_NAMESPACE(QPointer)<QT_PREPEND_NAMESPACE(QObject)> _instance; \
            if (!_instance) {    \
                QT_PLUGIN_RESOURCE_INIT \
                _instance = new IMPLEMENTATION; \
            } \
            return _instance; \
        }

#define QT_MOC_EXPORT_PLUGIN(PLUGINCLASS, PLUGINCLASSNAME) \
            Q_EXTERN_C Q_DECL_EXPORT \
            const char *qt_plugin_query_metadata() \
            { return reinterpret_cast<const char *>(qt_pluginMetaData); } \
            Q_EXTERN_C Q_DECL_EXPORT QT_PREPEND_NAMESPACE(QObject) *qt_plugin_instance() \
            Q_PLUGIN_INSTANCE(PLUGINCLASS)
```

两个导出函数的职责：

- `qt_plugin_query_metadata()`：返回编译进二进制的元数据（IID + JSON 内容），`QPluginLoader::metaData()` 读的就是它；
- `qt_plugin_instance()`：**`new IMPLEMENTATION` 就是创建插件实例的地方**。注意它用静态 `QPointer` 持有实例——插件实例整个进程只创建一次，`QPointer` 保证实例被外部销毁后不会返回悬空指针。

`QPluginLoader::instance()` 拿到的 `QObject*` 就来自第二个函数。静态插件（Qt 静态构建）写法略有差别，但导出函数的位置和职责相同。

## 6. 串起来：一次 qobject_cast 的完整旅程

把四个宏的产物拼成完整链路——主程序 `qobject_cast<EchoInterface*>(obj)` 发生了什么：

```
 主程序: qobject_cast<EchoInterface*>(obj)
        │  Q_DECLARE_INTERFACE 特化（§2）
        ▼
 obj->qt_metacast("org.qt-project...EchoInterface")
        │  IID 字符串传入
        ▼  moc 生成的代码内 strcmp 逐一比对（§4）
  ┌───────────────────────────────┐
  │ 匹配 IID 字符串?               │
  ├─ 是 ─▶ static_cast 转接口 ──▶ 返回接口指针
  └─ 否 ─▶ QObject::qt_metacast ─▶ 返回 nullptr
  └───────────────────────────────┘
```

回答 P1-06 的思考题"怎么确定转换出来的类型一定正确"：保证来自**唯一 IID 字符串匹配**——接口方和插件方写的是同一个 IID，strcmp 匹配成功才返回指针；匹配不上返回 nullptr，主程序判空即可安全失败，不会出现错误的强制转换。

## 7. 小结

```
 四个宏的本质回顾
 ├─ Q_DECLARE_INTERFACE：编译期模板特化，
 │   把 qobject_cast 引到 qt_metacast(IID)
 ├─ Q_PLUGIN_METADATA / Q_INTERFACES：纯标注，
 │   信息由 moc 编译期收集
 ├─ moc 产物一：qt_metacast() 的 strcmp 匹配分支
 ├─ moc 产物二（QT_MOC_EXPORT_PLUGIN）：
 │   qt_plugin_instance() / query_metadata() 两个导出函数
 └─ 安全性的根基：唯一 IID 字符串匹配，失败安全返回
     nullptr
```
