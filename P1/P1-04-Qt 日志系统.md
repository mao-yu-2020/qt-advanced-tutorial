# P1-04 Qt 日志系统

> 本文基于 **Qt 6.8.3**。日志是项目开发中非常重要的一环：调试期靠它看流程，
> 发布期靠它做事后排查。本篇讲 Qt 自带的日志系统；真实项目的 spdlog 异步
> 封装方案见 P3-01。

## 1. 为什么不用 qDebug() 一把梭

项目小的时候，`qDebug()` 确实够用了。但代码一多，问题就来了：

```
 满屏日志的困境
  [网络] 连接成功        ← 想要的
  鼠标移动 (512, 300)    ← 不想要的，刷屏
  [数据库] 查询耗时 3ms   ← 想要的
  鼠标移动 (513, 301)    ← 又把想要的顶没了
  ……
  ✘ 无法按模块开关：想看网络的，就得忍受所有的
  ✘ 发布后无法留存：程序一关，现场没了
```

Qt 日志系统给出的答案是：**消息按"类别（category）× 等级（type）"两个维度组织**，每个维度都能独立开关。我们常用的 `qDebug()` 打印的消息属于 `default` 类别——它等价于 `qCDebug(QLoggingCategory::defaultCategory())`。Qt 自身模块也都有自己的类别（名字以 `qt.` 开头），只是默认不打印。

```
           debug   info   warning   critical
 default     ✔      ✔        ✔         ✔
 driver.usb  ✔/✘    ✔/✘      ✔         ✔     ← 每个类别独立开关
 qt.*        ✘      ✔        ✔         ✔     ← qt.* 的 debug 默认关闭
```

这套"类别 × 等级"的二维开关，就是本篇的主线。

## 2. 一条消息的旅程

先看全貌——一条日志从宏到输出要走的路：

```
 ┌──────────────┐   qCDebug(lcUsb) << ...   ┌───────────────┐
 │  业务代码     │ ─────────────────────────▶│ QLoggingCategory│
 │  qCDebug 等   │                           │ 按类别+等级过滤  │
 └──────────────┘                           └──────┬────────┘
        未通过过滤的消息根本不会生成 ★                    ▼
                                              ┌───────────────┐
                                              │ message handler│
                                              │ 最终输出        │
                                              └───────────────┘
```

两个关键结论：

- **过滤在宏阶段就发生**：`qCDebug()` 等宏展开后先检查该类别该等级是否开启，未开启时**参数根本不会求值**——过滤是零成本的，高频日志放心加类别开关，但反过来也提醒：不要依赖日志参数的副作用（`qCDebug(lc) << compute();` 被过滤时 `compute()` 不会执行）。
- **输出由 handler 决定**：默认 handler 打印到 stderr/调试器，可以用 `qInstallMessageHandler` 完全接管。

## 3. 消息宏与消息等级

五个等级，语义递进：

```
 qDebug    ── 调试细节，发布版通常关闭
 qInfo     ── 正常的运行信息
 qWarning  ── 可恢复的异常，程序能继续
 qCritical ── 严重错误，功能已受损
 qFatal    ── 致命错误，打印后直接 abort ★不可捕获
```

每种宏都有两种写法，流式和 printf 式等价：

```cpp
qDebug() << "connected to" << host << "port" << port;
qInfo("connected to %s port %d", qPrintable(host), port);
```

带类别的版本对应为 `qCDebug(category)` / `qCInfo(category)` ……，§5 详述。

## 4. 自定义输出：qInstallMessageHandler

想改变日志的去向（写文件、转发到日志面板、上报服务器），安装自己的 handler：

```cpp
void myMessageOutput(QtMsgType type, const QMessageLogContext &context,
                     const QString &msg)
{
    QByteArray localMsg = msg.toLocal8Bit();
    const char *file = context.file ? context.file : "";
    const char *function = context.function ? context.function : "";
    const char *level = "debug";
    switch (type) {
    case QtDebugMsg:    level = "debug"; break;
    case QtInfoMsg:     level = "info"; break;
    case QtWarningMsg:  level = "warning"; break;
    case QtCriticalMsg: level = "critical"; break;
    case QtFatalMsg:    level = "fatal"; break;
    }
    fprintf(stderr, "[%s] %s (%s:%u, %s)\n",
            level, localMsg.constData(), file, context.line, function);
}

int main(int argc, char **argv)
{
    qInstallMessageHandler(myMessageOutput);   // 传 nullptr 恢复默认
    QApplication app(argc, argv);
    ...
}
```

```
 默认链路                        安装自定义 handler 后
 宏 → 过滤 → 默认handler→stderr   宏 → 过滤 → 你的handler → 去哪都行
                ▲                                ▲
        pattern 在这里生效 ★              pattern 不再自动生效 ★
```

三个使用要点：

1. **`qSetMessagePattern()` 对你不再自动生效**——格式化是默认 handler 内部做的事。想沿用 pattern，在 handler 里手动调 `qFormatLogMessage(type, context, msg)` 生成；
2. **handler 会被多个线程并发调用，必须可重入**——往同一个文件写要自己加同步；
3. **handler 里不要再打日志**——handler 内产生的日志会被忽略（防止递归）。

## 5. 日志类别 QLoggingCategory

### 5.1 声明与定义

类别机制的用法是一对宏的配合——头文件声明、一个 cpp 定义：

```cpp
// logcategories.h：所有用到的地方包含它
Q_DECLARE_LOGGING_CATEGORY(lcUsb)

// logcategories.cpp：只在一个 cpp 里定义
Q_LOGGING_CATEGORY(lcUsb, "driver.usb")

// 业务代码中使用
qCDebug(lcUsb) << "device enumerated:" << name;
qCWarning(lcUsb) << "transfer timeout, retrying";
```

宏背后的原理值得知道（知其然也知其所以然）：

```cpp
// Q_DECLARE_LOGGING_CATEGORY(name) 展开后是一个 extern 函数声明
extern const QLoggingCategory &name();

// Q_LOGGING_CATEGORY(name, string) 展开后是这个函数的定义
const QLoggingCategory &name()
{
    static const QLoggingCategory category(string);
    return category;
}
```

所以"类别"其实是一个返回静态 `QLoggingCategory` 的函数——函数名（`lcUsb`）和类别名（`"driver.usb"`）不必相同，但建议保持对应关系好维护。

类别命名遵守官方约定：只用字母和数字，点号分层（如 `driver.usb.events`）；不要用 `debug`/`info` 等作类别名；`qt` 前缀保留给 Qt 自身。

### 5.2 类别分流的效果

```
 业务代码                        类别开关（示例）
 ├─ qCDebug(lcNet)   ──▶ driver.net   *.debug=false
 ├─ qCDebug(lcUsb)   ──▶ driver.usb   driver.usb.debug=true
 └─ qCWarning(lcDb)  ──▶ storage.db   ────────────────
                                         结果：满屏 debug 全关，
                                         只看 usb 模块的 debug ★
```

这就是 §1 困境的解法：每个模块一个类别，排查哪个模块就开哪个模块。

## 6. 过滤规则：三套开关

### 6.1 规则语法

```cpp
// 语法：<category>[.<type>] = true|false
QLoggingCategory::setFilterRules(QStringLiteral("driver.usb.debug=true"));

// 多条规则用换行分隔，后面的覆盖前面的
QLoggingCategory::setFilterRules("*.debug=false\n"
                                 "driver.usb.debug=true");
```

类别名支持 `*` 通配符（只能出现在首尾）；等级可省略，省略表示该类别的所有等级。

### 6.2 规则的来源与优先级

同一个开关有五个来源，**优先级从低到高**：

```
 低  ┌────────────────────────────────────────┐
     │ 1. Qt 安装目录下的 qtlogging.ini         │
     │ 2. QtProject/qtlogging.ini（用户配置目录）│
     │ 3. 代码里 setFilterRules()               │
     │ 4. QT_LOGGING_CONF 环境变量指定的配置文件 │
 高  │ 5. QT_LOGGING_RULES 环境变量             │
     └────────────────────────────────────────┘
      高层覆盖低层 ★——代码里写死的规则可能被环境变量推翻
```

配置文件和环境变量的写法：

```ini
# qtlogging.ini
[Rules]
*.debug=false
driver.usb.debug=true
```

```bash
# 环境变量多条规则用分号分隔
QT_LOGGING_RULES="*.debug=false;driver.usb.debug=true"
```

这个设计的实战价值：**不改代码、不重编译，就能在现场打开某个模块的日志**——发布后排查问题的关键能力。规则到底从哪加载的搞不清楚时，设 `QT_LOGGING_DEBUG` 环境变量，Qt 会自己打印加载来源。

顺带解释一个常见疑惑：**为什么 Qt 模块自己的 debug 日志平时看不到？** 因为 Qt 的默认过滤逻辑里硬编码了"`qt` 或 `qt.` 开头的类别，debug 一律关闭"。想看的话，一条 `qt.*.debug=true` 规则即可。

### 6.3 installFilter：完全接管（慎用）

```cpp
QLoggingCategory::CategoryFilter installFilter(
    QLoggingCategory::CategoryFilter filter);
```

不想用文本规则、想按自己的方式（比如读数据库配置）控制类别开关，可以安装自定义过滤函数。注意：**安装后所有文本规则都会被忽略**，包括用户的环境变量——相当于把上面五个来源全部废掉，建议谨慎。

## 7. 消息格式：qSetMessagePattern

默认 handler 的输出格式可以定制：

```cpp
qSetMessagePattern("[%{time h:mm:ss.zzz}] %{type} [%{category}] "
                   "%{message} (%{file}:%{line})");
// 输出示例：
// [14:03:22.451] debug [driver.usb] device enumerated: xxx (usb.cpp:87)
```

常用占位符：

| 占位符 | 说明 |
| --- | --- |
| `%{type}` | debug / info / warning / critical / fatal |
| `%{category}` | 类别名 |
| `%{message}` | 消息内容 |
| `%{file}` / `%{line}` / `%{function}` | 源码位置 |
| `%{appname}` / `%{pid}` / `%{threadid}` | 应用名 / 进程 / 线程 ID |
| `%{time [format]}` | 系统时间，format 同 `QDateTime::toString` |
| `%{time process}` | 进程启动以来的秒数 |
| `%{backtrace [depth=N]}` | 调用回溯（部分平台可用） |

还有条件输出：`%{if-debug}`…`%{endif}` 内的内容只在对应等级打印。默认 pattern 就是 `%{if-category}%{category}: %{endif}%{message}`——这就是为什么 qDebug() 输出只有消息本身。

两个坑：

1. **`%{file}`/`%{line}`/`%{function}`/`%{category}` 依赖编译期的 `QT_MESSAGELOGCONTEXT`**——默认只有 Debug 构建记录这些上下文，Release 里打出来是空的。Release 也要用就显式定义该宏（反之 `QT_NO_MESSAGELOGCONTEXT` 可强制关闭）；
2. pattern 也能用 **`QT_MESSAGE_PATTERN` 环境变量**在运行时设置，且环境变量优先——不改代码临时调格式，排查利器。

## 8. 实战边界与红线

- **线程安全**：消息宏本身线程安全，但 handler 会被多线程并发调用（§4）；
- **性能**：类别过滤在宏阶段短路，被关掉的日志零成本；但**开着的**高频日志是真开销——同步写 stderr 会阻塞调用线程；
- **什么时候该上专业日志库**：当你需要异步写盘、按大小轮转、崩溃时留存现场、按类别拆分文件——Qt 自带系统就到边界了。真实项目里我们通常用 spdlog 封装一层，并用 `qInstallMessageHandler` 把 Qt 消息（包括 Qt 框架自身的告警）一并捕获进统一日志。完整方案见 P3-01。

## 9. 小结

```
 本文要点回顾
  ├─ 组织方式：类别 × 等级 二维开关，过滤在宏阶段零成本
  ├─ 五个等级：debug < info < warning < critical < fatal
  ├─ 输出接管：qInstallMessageHandler（可重入、不递归、
  │            pattern 需手动 qFormatLogMessage）
  ├─ 类别：Q_DECLARE/Q_LOGGING_CATEGORY 一头一 cpp 配套
  ├─ 过滤：五个来源，环境变量 > 代码 > 配置文件
  └─ 格式：qSetMessagePattern / QT_MESSAGE_PATTERN；
           源码位置信息依赖 QT_MESSAGELOGCONTEXT
```
