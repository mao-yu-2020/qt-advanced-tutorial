# P1-02 事件循环与线程模型

> 本文基于 **Qt 6.8.3**。本篇是全套教程的地基：理解了事件循环和线程亲和性，
> 后面的多线程（P1-03）、信号槽机制（P1-01）才真正讲得通。
> 深入原理见 P2-02（事件循环的源码实现）。

## 1. 程序为什么"什么都不点也在运行"

先看两种程序的执行模型对比：

```
 控制台程序                       GUI 程序
 ┌──────────────┐               ┌──────────────┐
 │ main() 开始   │               │ main() 开始   │
 │   ↓ 顺序执行  │               │   ↓ 初始化    │
 │ 任务做完      │               │ exec() 进入   │
 │   ↓          │               │  ★ 永不退出   │
 │ return 退出   │               │  的循环       │
 └──────────────┘               │   ↓ 收到退出   │
  代码跑完，进程结束              │ return 退出   │
                                └──────────────┘
                                 没事件时也在"活着"
```

控制台程序的生命是"任务"的：代码跑完，进程结束。而 GUI 程序启动后，即使你什么都不点，它也不会退出——它在**等**。等鼠标点击、等键盘输入、等定时器到点、等网络数据到达。

这个"永远等着、随时响应"的机制，就是**事件循环**。`QCoreApplication::exec()` 启动它，`quit()` 结束它。可以说：**Qt 程序 = 初始化 + 一个事件循环**，你写的所有槽函数、事件处理，都只是挂在这个循环上的"响应"。

## 2. 事件循环是什么

事件循环的概念模型简单到只有三步：

```
        ┌─────────────────────────────┐
        ▼                             │
   ┌─────────┐   ┌─────────┐   ┌─────────┐
   │ 取事件   │──▶│ 分发给   │──▶│ 对象的   │
   │（没有就睡）│   │ 目标对象 │   │ 处理函数 │
   └─────────┘   └─────────┘   └─────────┘
        ▲                             │
        └─────────────────────────────┘
              收到 quit 才退出循环
```

- **取事件**：从本线程的事件队列里取下一个事件；队列空时线程挂起睡眠，不占 CPU；
- **分发**：根据事件的接收者（receiver）找到目标 QObject；
- **处理**：调用 `receiver->event()`，进而分到具体处理函数（`mousePressEvent`、`timerEvent`、槽函数……）。

事件的来源有四类：

```
 事件来源
  ├─ 系统输入：鼠标、键盘、触摸（操作系统投递）
  ├─ 定时器：QTimer / startTimer 到点
  ├─ 系统通知：网络数据可读、窗口重绘请求
  └─ Qt 内部 post：队列连接的信号槽、元调用、
     deleteLater、QCoreApplication::postEvent ★
```

最后一类是重点：**Qt 自己的异步机制全部建立在"post 事件"之上**。跨线程信号槽、元调用、延迟删除，本质都是往目标线程的事件队列里放了一个事件。理解了这一点，后面所有异步套路都迎刃而解——这也是本文称事件循环为"Qt 一切异步机制的发动机"的原因。

一个常见误解需要澄清：**事件循环空转时线程在睡觉，不占 CPU**。"循环"描述的是行为模型，不是 `while(true)` 死转。队列空时，线程阻塞在操作系统的等待原语上（Windows 是 `MsgWaitForMultipleObjectsEx`），有事件到来才被唤醒。

## 3. 每条线程一个事件循环

事件循环不是全程序一个，而是**每条线程各有一套**：

```
   主线程                    子线程 A
 ┌──────────────┐         ┌──────────────┐
 │ 事件队列      │         │ 事件队列      │
 │ 事件分发器    │         │ 事件分发器    │
 │ 事件循环      │         │ 事件循环      │
 │ 挂着的对象们  │         │ 挂着的对象们  │
 └──────────────┘         └──────────────┘
   各自独立运转，互不干扰（底层靠线程局部存储，
   源码细节见 P2-02）
```

哪些线程有事件循环？

```
 线程类型                有事件循环？
 ├─ 主线程               ✔ exec() 启动
 ├─ QThread::start()    ✔ run() 默认调 exec()
 ├─ QThreadPool 的线程   ✘（任务循环，跑完即还）
 └─ 裸 std::thread       ✘（除非自己创建 QEventLoop）
```

"这条线程有没有事件循环"是一个极其重要的判别标准——它直接决定这条线程**能不能接收队列连接的信号、能不能用定时器、允不允许阻塞等待**。这个标准在 P1-03 的线程实践里会反复用到。

## 4. 线程亲和性

Qt 里每个 QObject 都"属于"一条线程——`QObject::thread()` 返回它所属的那条。这个归属关系叫**线程亲和性**（thread affinity）。

对象默认属于**创建它时所在的线程**：主线程里 new 的对象属于主线程，子线程里 new 的属于子线程。

```
   主线程                    子线程 A
 ┌──────────────┐         ┌──────────────┐
 │  事件循环     │         │  事件循环     │
 │   ├ window   │         │   └ worker   │
 │   ├ button   │         │      ↑       │
 │   └ model    │         │  属于这条线程 │
 └──────────────┘         └──────────────┘
      各对象的事件各回各家：发给 worker 的事件
      进子线程 A 的队列，由 A 的循环分发
```

亲和性决定三件事：

1. **槽函数在哪条线程执行**——队列连接的槽，在 receiver 所属线程的循环里执行；
2. **定时器在哪触发**——`QTimer` 的超时在它所属线程的循环里触发；
3. **事件发给谁**——post 给某对象的事件，进入它所属线程的队列。

`QObject::moveToThread()` 可以改变对象的亲和性（连带所有子对象一起迁移）。这是多线程实践的核心操作，具体用法和坑在 P1-03 展开，这里只需记住：**亲和性决定"代码在哪条线程跑"**。

两个派生规则：

- **有 parent 的对象不能 moveToThread**——父子必须同属一条线程；
- 跨线程**直接调用**对方对象的成员函数，函数在**调用者**线程执行——亲和性管不住直接调用，这正是"禁止跨线程直接调用"这条红线存在的原因。

## 5. 直接连接 vs 队列连接

信号槽连接类型把"亲和性"和"事件循环"串了起来。先看两种基本行为：

```
 DirectConnection（直接）        QueuedConnection（队列）
 ┌───────────────────┐         ┌───────────────────┐
 │ emit 信号          │         │ emit 信号          │
 │   ↓ 立即、同步      │         │   ↓ 打包成事件      │
 │ 在发射者线程执行槽  │         │ 投入 receiver 所在  │
 │   ↓               │         │ 线程的事件队列      │
 │ emit 返回时槽已跑完 │         │   ↓ 该线程循环分发  │
 └───────────────────┘         │ 在 receiver 线程    │
  像一次普通函数调用             │ 执行槽              │
                               └───────────────────┘
                                像寄了一封信：先发后收
```

队列连接的时序值得细看——它是"先排队、后执行"：

```
 发射线程              时间轴              receiver 线程
    │ emit ──▶ 事件入队 ─────────────▶ 队列里等待
    │ 继续往下跑（不等待）    ……            ↓ 循环分发
    │                                槽函数执行 ✔
```

默认的 `Qt::AutoConnection` 规则一句话说清：**发射时 receiver 和当前线程相同 → 直接连接；不同 → 队列连接**。这意味着：

> **同线程的信号槽是同步函数调用，跨线程的信号槽自动变成异步消息——这就是 Qt 跨线程通信安全的根基。**

还有两个连接类型知道即可：

- `Qt::BlockingQueuedConnection`：队列连接，但发射者**阻塞**等槽执行完。要求双方不同线程且极易死锁（receiver 线程一旦也在等发射者，就抱死了），实际项目里基本不该出现；
- `Qt::UniqueConnection`：不是行为类型而是修饰位，防止重复 connect，可与上面组合使用。

一个连带结论：跨线程连接想用**直接连接**（在发射线程执行槽）虽然语法允许，但等于亲手拆掉 Qt 的保护，绝大多数情况下是 bug 的温床。

## 6. 事件循环与异步编程

### 为什么"有事件循环的线程禁止阻塞"

把 §2 的图再看一眼：循环上的所有对象**共享同一个分发通道**。任何一个处理函数阻塞了，整个循环就停摆——定时器不走了、队列连接的信号堆积了、UI 不刷新了。

```
 循环停摆的连锁反应

 槽函数阻塞 5 秒
   ├─ 队列里的事件全部排队干等
   ├─ 同线程其它对象的定时器/槽全部失灵
   └─ 若这是主线程 → 界面冻结
```

所以 P1-03 的那条判别标准在这里得到解释：**判别一条线程能不能阻塞，就看它有没有事件循环**。有循环的线程，阻塞伤害的是这条线程上的所有人；没有循环的裸线程（如管线级 `std::thread`），阻塞只影响自己，反而可以用来做背压。

### 嵌套事件循环："套娃"是怎么回事

`QEventLoop::exec()` 可以在当前函数里再开一层事件循环，实现"原地等待某个条件，又不卡死外层循环"：

```
 线程的事件循环栈
 ┌──────────────────────────┐
 │ QEventLoop(内层) ← 你在等 │   栈顶：当前运行的循环
 │ QEventLoop(外层，如主循环) │
 └──────────────────────────┘
      两层共享同一个事件分发器 ★
      事件照常分发，外层并不"卡死"
```

`QDialog::exec()` 就是这么实现模态对话框的。但请注意规范：**对外接口里禁止用嵌套循环等异步结果**（P1-03 的异步接口红线）。原因有二——它把异步时序伪装成同步代码，重入问题（等待期间别的槽照样触发）会咬人；它让调用方误以为"这函数会阻塞"，破坏全异步的调用约定。机制可以用，但不能出现在接口边界上。

### 串起来：异步三件套的地基

到这里，P1-03 的"异步三件套"各自的地基都齐了：

```
 三件套                    地基（本文）
 ├─ 信号与槽      ←──── 队列连接 = post 事件到对方循环
 ├─ 元调用         ←──── invokeMethod(Queued) = 同上
 └─ std::function 回调 ←─ 结果由循环里的代码调用，
                          天然落在对的线程
```

## 7. 小结

```
 本文要点回顾
  ├─ GUI 程序 = 初始化 + 一个永不退出的事件循环
  ├─ 事件循环：取事件 → 分发 → 处理；空转时睡眠不占 CPU
  ├─ 每条线程一套循环；线程池/裸线程没有
  ├─ 亲和性：QObject 属于一条线程，决定槽/定时器/事件的去处
  ├─ AutoConnection：同线程同步调用，跨线程自动变异步消息
  └─ 红线：有事件循环的线程禁止阻塞
```
