# P1-06 Qt 插件机制

> 本文基于 **Qt 6.8.3**。插件是 Qt 工程化的重要一环：Qt 自身靠插件扩展
> （数据库驱动、图片格式、平台集成），应用程序也可以用同样的机制解耦自己
> 的功能模块。宏的源码级分析见 P2-03，MySQL 驱动编译实战见 P3-05。

## 1. 插件解决什么问题

先想象一个需求：主程序要支持多种数据导出格式，格式还在不断增加。如果把每种格式都写死在主程序里，每加一种格式就要改主程序、重新发布。插件机制给出的结构是：

```
 ┌───────────┐        ┌──────────┐
 │ 主程序     │───────▶│ 抽象接口  │
 │ (启动时不带 │        │ (纯虚类)  │
 │  任何格式)  │        └────┬─────┘
 └───────────┘              │ 运行时按需加载
              ┌────────────┼────────────┐
              ▼            ▼            ▼
         ┌────────┐  ┌────────┐   ┌────────┐
         │插件dll: │  │插件dll: │   │插件dll: │
         │ CSV    │  │ JSON   │   │ 新格式  │
         └────────┘  └────────┘   └────────┘
```

插件是动态库的一种延伸——基于操作系统"动态加载/卸载库"的能力，Qt 在上面定了一套规范：**插件必须是动态库，由程序在运行中动态加载（而非启动时链接），实现类继承 QObject 并暴露统一的接口**。

Qt 插件分两个层级：

```
 Qt 插件体系
 ├─ 低级插件（Low-Level）：扩展【你自己的应用】
 │    自定义接口 + QPluginLoader 加载（本篇主线）
 └─ 高级插件（Higher-Level）：扩展【Qt 自身】
      继承 Qt 指定的插件基类（数据库驱动、图片格式……）
```

一个绕不开的现实问题：**二进制兼容**。插件 dll 和主程序 exe 必须用同一编译器、同样的编译选项和运行库——这是插件开发和排查加载失败的背景知识，§5 的排查清单会反复用到它。

## 2. 插件三要素与四个宏

一个 Qt 插件由三样要素组成：

```
 ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
 │ ① 接口定义    │   │ ② 插件实现    │   │ ③ 主程序加载  │
 │ 纯虚类 + IID  │   │ 实现接口的    │   │ QPluginLoader │
 │              │   │ QObject 类   │   │ 加载并转换    │
 └──────────────┘   └──────────────┘   └──────────────┘
```

支撑这三样要素的是四个宏，先看清分工（底层实现见 P2-03）：

```
  Q_DECLARE_INTERFACE  接口侧：把接口类与唯一 IID 字符串关联，
                       特化 qobject_cast<接口*>()

  Q_INTERFACES         插件侧：声明插件类实现了哪些接口，
                       moc 据此生成类型匹配代码

  Q_PLUGIN_METADATA    插件侧：声明插件元数据（IID、JSON 文件），
                       供 QPluginLoader::metaData() 读取

  QT_MOC_EXPORT_PLUGIN moc 产物：生成两个 dll 导出函数
                       （qt_plugin_instance / query_metadata）
```

记住一句话：**接口侧注册 IID，插件侧声明实现和元数据，moc 负责生成胶水代码**。

## 3. 完整实例：EchoPlugin

以 Qt 官方示例 EchoPlugin 为例，走一遍全流程。

### 3.1 接口定义

接口是一个纯虚类，用 `Q_DECLARE_INTERFACE` 关联一个全局唯一的 IID 字符串：

```cpp
// echointerface.h
#include <QString>

class EchoInterface
{
public:
    virtual ~EchoInterface() = default;
    virtual QString echo(const QString &message) = 0;
};

#define EchoInterface_iid "org.qt-project.Qt.Examples.EchoInterface"
Q_DECLARE_INTERFACE(EchoInterface, EchoInterface_iid)
```

### 3.2 插件实现

插件类**同时继承 QObject 和接口类**，三个宏各司其职：

```cpp
// echoplugin.h
#include <QObject>
#include <QtPlugin>
#include "echointerface.h"

class EchoPlugin : public QObject, EchoInterface
{
    Q_OBJECT
    Q_PLUGIN_METADATA(IID "org.qt-project.Qt.Examples.EchoInterface"
                      FILE "echoplugin.json")
    Q_INTERFACES(EchoInterface)

public:
    QString echo(const QString &message) override;
};
```

`FILE` 指向的 JSON 元数据（`echoplugin.json`）会被编译进插件二进制——主程序**不加载插件**也能通过 `metaData()` 读到它，常用来声明插件能力：

```json
{ "Keys": [ "echoplugin" ] }
```

★ 一条铁律：**`Q_PLUGIN_METADATA` 的 IID 必须与接口里 `Q_DECLARE_INTERFACE` 的 IID 一字不差**，否则主程序侧转换拿不到接口指针。

### 3.3 主程序加载

```cpp
#include <QCoreApplication>
#include <QPluginLoader>
#include <QDebug>
#include "echointerface.h"

int main(int argc, char *argv[])
{
    QCoreApplication app(argc, argv);

    QPluginLoader loader(QStringLiteral("echoplugin.dll"));
    if (!loader.load()) {
        qWarning() << "插件加载失败:" << loader.errorString();
        return -1;
    }

    QObject *plugin = loader.instance();
    EchoInterface *echo = qobject_cast<EchoInterface *>(plugin);
    if (!echo) {
        qWarning() << "插件没有实现 EchoInterface 接口";
        return -1;
    }

    qDebug() << echo->echo(QStringLiteral("hello plugin"));
    qDebug() << "metaData:" << loader.metaData();   // 读 JSON 元数据
    return 0;
}
```

加载时序的完整画面：

```
 主程序 exe   QPluginLoader        插件 dll
 ┌───────────┐               ┌─────────────┐
 │ load()    │── 动态加载 ──▶ │ qt_plugin_  │
 │ instance()│◀── 返回 ─────  │  instance() │
 └─────┬─────┘   QObject*    │ qt_plugin_  │
       ▼                     │  query_     │
 ┌───────────┐               │  metadata() │
 │qobject_cast│              └──────┬──────┘
 │ 转接口指针 │                     │ new 出
 └───────────┘                     ▼
                            接口实现对象
                           （继承 QObject）★
```

`instance()` 返回的为什么是 `QObject*`？因为插件实例是 moc 生成的导出函数 new 出来的，导出函数只有 C  ABI，`QObject*` 是双方都能懂的"通用货币"；随后靠元对象系统（`qobject_cast` → IID 字符串匹配）安全地换回接口指针。这也是"实现类必须继承 QObject"的根本原因。

## 4. 高级插件：扩展 Qt 自身

高级插件机制完全一样，只是接口不是自己定义的，而是**继承 Qt 指定的插件基类**，一般实现基类规定的 `create()` 方法即可：

| 插件基类 | 用途 |
| --- | --- |
| `QSqlDriverPlugin` | 数据库驱动（如 MySQL 驱动） |
| `QImageIOPlugin` | 图片格式读写 |
| `QPlatformIntegrationPlugin` | 平台集成（窗口系统适配） |
| `QStylePlugin` | 自定义控件风格 |
| `QIconEnginePlugin` | 自定义图标引擎 |

Qt 按**目录约定**发现这些插件：如数据库驱动放 `plugins/sqldrivers/`、图片格式放 `plugins/imageformats/`。可用 `QCoreApplication::libraryPaths()` 查看实际扫描路径。

最常被问到的高级插件是 **MySQL 驱动**：Qt 官方二进制包不自带它（Qt 6 只附带 SQLite，Windows 另有 ODBC/PostgreSQL），需要自己用 Qt 源码单独编译——完整编译步骤和分发注意事项见 **P3-05**。

## 5. 常见问题与调试

"插件编译成功却加载失败"是最常见的坑。两件排查武器：

1. **`loader.errorString()`**——加载失败后第一手的失败原因；
2. **`QT_DEBUG_PLUGINS=1`** 环境变量——Qt 会输出详细的插件扫描日志（扫了哪些目录、哪个插件因为什么被拒绝）。

按这张清单逐项检查，九成问题能定位：

```
 插件加载失败排查清单
 ├─ 位数一致?     32位 exe 不能加载 64位 dll，反之亦然
 ├─ 编译器一致?   MSVC 插件不能配 MinGW 程序；
 │                MSVC 下 debug/release 运行库也不能混用
 ├─ IID 一致?     Q_PLUGIN_METADATA 的 IID 与接口
 │                Q_DECLARE_INTERFACE 的 IID 一字不差
 ├─ 依赖可达?     插件依赖的底层 dll（如 libmysql.dll）
 │                要在 exe 目录或 PATH 中
 │               （可用 Dependencies / dumpbin 查看依赖）
 └─ 目录正确?     用 QCoreApplication::libraryPaths()
                  确认 Qt 实际扫描的插件目录
```

对 SQL 驱动类插件，还可以叠加 `QT_LOGGING_RULES=qt.sql.*.debug=true`（P1-04 的过滤规则）打开 SQL 子系统的调试输出。

## 6. 小结

```
 本文要点回顾
  ├─ 插件 = 运行时动态加载的 dll + Qt 规范（QObject 实现类）
  ├─ 三要素：接口(Q_DECLARE_INTERFACE) → 实现(Q_INTERFACES
  │   + Q_PLUGIN_METADATA) → 加载(QPluginLoader)
  ├─ 两个层级：低级（扩展自己应用）/ 高级（扩展 Qt 自身）
  ├─ 二进制兼容是插件的阿克琉斯之踵
  └─ 排查：errorString() + QT_DEBUG_PLUGINS=1 + 五项清单
```

**思考题**

1. 为什么 Qt 插件的实现类必须继承 QObject？（提示：从 `QPluginLoader::instance()` 的返回类型和 `qobject_cast` 的依赖逆推）
2. Qt 插件 dll 和传统 dll 有什么区别？"固定导出两个 C 函数"的设计换来了什么？
3. `qobject_cast` 怎么保证转换出来的接口类型一定是对的？匹配失败时会发生什么？

<details><summary>参考思路</summary>

1. `instance()` 返回 `QObject*`，实现类必须继承 QObject；`qobject_cast` 依赖 moc 元对象系统做 IID 匹配，这也要求 QObject 体系。
2. 传统 dll 直接导出函数/类，启动时链接加载；插件 dll 固定导出 `qt_plugin_instance()` / `qt_plugin_query_metadata()`，换来运行时的动态加载与卸载能力。
3. 靠唯一 IID 字符串匹配：moc 生成的 `qt_metacast()` 内 strcmp 逐一比对，匹配上才 `static_cast` 返回接口指针，匹配不上返回 nullptr——失败是安全的判空，不会出现错误强转。

</details>
