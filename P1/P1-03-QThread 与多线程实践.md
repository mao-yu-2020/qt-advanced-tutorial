# P1-03 QThread 与多线程实践

> 本文基于 **Qt 6.8.3**。事件循环、线程亲和等概念见 P1-02；本文专注"线程怎么用"。
> 深入原理见 P2-02（QThread 与事件循环的源码实现）；落地案例见 P3-02（数据库 Worker 实战）。

## 1. 为什么绕不开线程

先看一个几乎所有 Qt 开发者都踩过的坑：在按钮槽函数里执行一个耗时操作——

```
 主线程时间轴（错误写法）

 点击按钮 ──▶ 槽函数开始 ──▶ 耗时任务 3 秒 ──▶ 槽函数返回
                                │
                    这 3 秒内事件循环停摆 ★
                    界面不刷新、点击无响应、动画冻结
```

主线程的本质是一个事件循环（详见 P1-02）：UI 刷新、输入响应、定时器、信号槽投递，全靠它一轮轮转。你在主线程里塞一个 3 秒的耗时任务，等于把循环按停 3 秒——界面"卡死"不是 bug，是必然结果。

所以多线程在 Qt 里不是性能优化选项，而是**正确性要求**：耗时的事，必须离开主线程。

## 2. Qt 的线程版图

Qt 的线程设计非常明确，先记住这一句话：**一条主线程，N 条后台线程，一个执行函数任务的线程池**。

```
 ┌────────────────────────────────────────────┐
 │                Qt 线程版图                  │
 ├────────────────────────────────────────────┤
 │ 主线程 × 1   ── 所有 UI 操作必须在这里      │
 │ 子线程 × N   ── 网络 IO / 数据库等长任务    │
 │ 线程池 × 1   ── 短平快的函数任务（全局）    │
 └────────────────────────────────────────────┘
```

### 主线程

`main()` 所在的线程。特殊之处只有一条铁律：**一切 UI 操作都只能在这条线程上进行**。

有些限制很隐晦。比如 `QWidget::update()` 只允许主线程调用；再比如日志面板这类控件——日志的格式化和刷新本质是 UI 操作，放子线程就有安全问题。

对主线程的两条禁令：

1. **不要在主线程执行耗时任务**——UI 卡顿，如上节；
2. **不要把网络、数据库对象关联在主线程**——它们的 IO 等待会拖慢事件循环。

### 子线程（后台线程）

适合放网络 IO 收发、数据库操作这类长生命周期任务。注意一个常见误解：子线程虽然"可以有 N 条"，但一个程序实际需要的后台线程数量是明确的——它是**长期存在的事件循环**，不是用完就扔的临时工。

经验值（非硬性规则）：**1~3 条后台线程足以应付绝大多数需求**。如果你的子线程很多，大概率是哪里设计出了问题——或者你在频繁地创建和销毁线程。

### 线程池

有了主线程和子线程，为什么还需要线程池？因为 Qt 严格区分两种循环：

```
  主线程 / 子线程                 线程池
 ┌──────────────────┐        ┌──────────────────┐
 │    事件循环       │        │    任务循环       │
 │ 信号槽/事件/定时器 │        │  来任务→执行→完   │
 │ 不能跑耗时任务 ★  │        │  适合耗时任务 ✔   │
 └──────────────────┘        └──────────────────┘
```

事件循环上绑着许多对象，一个任务耗时太久会拖累同一循环上的所有对象。短平快的耗时函数（压缩一个文件、算一次哈希）不值得为它养一条专属线程——丢进线程池，执行完即还。

Qt 提供全局线程池 `QThreadPool::globalInstance()`，一般不需要自己创建。

## 3. QThread 的正确打开方式

### 两种用法对比

```
 用法一：子类化 run()（旧式）   用法二：Worker + moveToThread（推荐）
 ┌─────────────────────┐      ┌─────────────────────┐
 │ class T : QThread   │      │ QThread 只管线程     │
 │ 重写 run() 干活      │      │ Worker(QObject) 干活 │
 │ ✘ 无线程事件循环*    │      │ ✔ Worker 有事件循环  │
 │ ✘ 信号槽语义混乱     │      │ ✔ 信号槽语义清晰     │
 │ ✘ 对象生死在两条线程 │      │ ✔ 职责单一          │
 └─────────────────────┘      └─────────────────────┘
 * run() 里不写 exec() 就没有事件循环
```

`QThread::run()` 默认实现就是调用 `exec()` 开启事件循环。**绝大多数情况下你不需要重写 `run()`**——把 `QThread` 当作"一条事件循环线程"的句柄，真正的活交给 `moveToThread()` 进来的 Worker 对象。

`QObject::moveToThread()` 改变对象的**线程亲和性**：之后该对象的槽函数、定时器、投递给它的事件，都在目标线程执行。默认情况下，QObject 创建时绑定的是**创建它所在的线程**。

两个容易踩的点：

- `moveToThread()` 之后，该对象的**所有子对象会一起迁移**；反过来，**有 parent 的对象不能被 move**——所以 Worker 构造时强制无 parent。
- **线程亲和性不同的两个 QObject，不能建立父子关系**（Qt 会直接报错）。

`QThread::start()` 可以指定线程优先级。后台线程保持默认即可——过高的优先级会抢占系统资源，拖累整体。

### 生命周期时序

```
 start() ──▶ 线程启动 ──▶ run() ──▶ exec() 事件循环运转
                                        │
        quit() ──▶ 循环退出 ──▶ finished 信号 ──▶ wait() 回收
                                        │
        ★ QThread 对象本身还活在创建它的线程里，
          销毁常用 deleteLater() 配合 finished 信号：
          connect(thread, &QThread::finished,
                  thread, &QObject::deleteLater);
```

### Qt 6 的便捷入口：QThread::create

Qt 6.0 起提供 `QThread::create()`，可以直接用 lambda 创建并启动一条线程，适合"不需要事件循环、跑完一个函数就结束"的场景：

```cpp
// Qt 6.8.3：一次性函数任务，比子类化 QThread 干净得多
auto *thread = QThread::create([] {
    doHeavyWork();
});
connect(thread, &QThread::finished, thread, &QObject::deleteLater);
thread->start();
```

注意：`QThread::create` 的函数体里同样没有事件循环——需要事件循环就回到 Worker 模式；只是一次性短任务，更推荐直接用线程池。

### 常见错误清单

- ✘ 在主线程**直接调用** Worker 的成员函数（绕过队列，函数在主线程执行）
- ✘ 跨线程直接 `delete` 对象（应 `deleteLater()`）
- ✘ Worker 构造函数里 new 子对象（此时对象还在主线程，见 §6.1）
- ✘ 给 Worker 设置 parent 后再 `moveToThread`（运行时报错且 move 失败）

## 4. 线程安全工具箱

数据跨线程共享就离不开同步原语。Qt 提供的一套工具先混个脸熟：

```
 共享状态是什么？
  ├─ 简单标志/计数 ──▶ QAtomicInteger / std::atomic（无锁）
  ├─ 读多写少的表 ──▶ QReadWriteLock（读读并发，读写互斥）
  ├─ 一般共享数据 ──▶ QMutex + QMutexLocker（RAII 防忘解锁）
  └─ 等某个条件   ──▶ QWaitCondition（队列非空/未满的挂起唤醒）
```

但请记住选型原则：**首选信号槽队列连接和元调用做跨线程通信，锁是最后手段**。锁保护的是"数据"，而队列连接传递的是"消息"——Qt 程序里绝大多数跨线程需求是后者。能用消息说清楚的事，不要共享数据。

这些原语的实战场景在 §6.4 的生产者-消费者管线里：有界队列靠条件变量做阻塞唤醒，退出流程靠原子 abort 标志驱动。

## 5. 任务该放哪条线程？

拿到任务先选型再动手。对照这张图决策：

```
 任务是什么性质？
  ├─ UI 操作 ─────────────▶ 主线程（没得选）
  ├─ 长生命周期、常驻
  │   （网络/数据库连接）─▶ 专属 QThread + 包装对象（§6.1）
  ├─ 单发、短平快 ────────▶ QThreadPool（用完即还）
  └─ 多级流水线、持续数据流
      （音视频解码渲染）──▶ 生产者-消费者管线（§6.4）
```

下一节就是这张图的展开：每种选型对应一套标准写法。

## 6. 线程实践模式

### 6.1 模式一：包装对象 + Worker（核心模式）

长生命周期任务的标准姿势，由两个职责严格分离的角色组成：

```
   主线程                         子线程
 ┌──────────────┐  元调用(Queued) ┌──────────────┐
 │     Xxx       │ ─────────────▶ │  XxxWorker   │
 │  （包装对象）  │                │  （执行体）   │
 │ 普通 QObject  │ ◀───────────── │ moveToThread │
 │ 不含线程代码  │  信号/元调用回传 │  干真正的活   │
 └──────────────┘                └──────────────┘
```

**包装对象**（对外，主线程）：

- 就是一个普通 QObject——可有 parent、走父子树、公开方法直接从主线程调用；
- **自身不含任何线程感知代码**（不出现 `moveToThread` / `QThread::currentThread` / `deleteLater`）；
- 公开方法统一用 `QMetaObject::invokeMethod(worker, ..., Qt::QueuedConnection)` 转发给 Worker；
- 对外状态信号由 Worker 转发而来，保证从主线程发出。

**Worker 执行体**（内部，子线程）：

- 统一 **`XxxWorker` 后缀**命名（禁止 `XxxPrivate`——`Private` 在 Qt 生态指 d-pointer 私有实现，用于跨线程执行体会语义误导）；
- 构造即 `moveToThread` 到专属子线程、**强制无 parent**、由包装对象析构时 `deleteLater` 销毁；
- 结果回调统一经元调用编组回主线程。

**初始化时机有个坑**：Worker 的构造函数体仍在主线程执行，**禁止在构造体里 new 子对象**——子对象会跟着落主线程。推荐写法是构造末尾把 `init()` 排队到子线程事件循环：

```cpp
XxxWorker::XxxWorker()
    : QObject(nullptr)   // 强制无 parent：有 parent 的对象禁止跨线程 move
{
    moveToThread(NetworkUtils::networkThread());
    QMetaObject::invokeMethod(this, &XxxWorker::init, Qt::QueuedConnection);
}

void XxxWorker::init()   // 在子线程执行，可正常创建子对象、连接信号
{
    m_client = new QMqttClient(this);
}
```

备选写法是惰性创建：子对象在首次用到的私有 getter 里创建（该 getter 只在子线程上下文被调用），适合初始化依赖后续调用入参的场景。

对使用者来说，整个过程**线程无感**：`new Xxx(this)` 挂上父子树、直接调用、随父对象析构。线程问题被完整封装在模式内部——这正是这套模式的价值。

### 6.2 模式二：异步接口设计

无法立即返回的操作，对外**只提供异步形式**：

```cpp
void start(const Req &req, std::function<void(const Resp &)> cb);
```

四条规则：

1. **禁止阻塞式公开接口**——接口里不出现 `waitForFinished`、`QEventLoop::exec()` 这类持等待预期的调用；
2. **单回调承载成败两态**——结果参数自带 `ok` 标志 + 语义化错误码（`enum class`）；禁止失败静默，也禁止拆成功/失败两个回调让调用方猜时序；
3. **回调保证从主线程发出**；回调内捕获对象一律用 `QPointer` 守卫，防止对象销毁后回调触发野指针；
4. 回调要交给子线程使用时，**随线程函数参数传递**，禁止用成员变量中转——成员变量的职责是"对象的状态"，而回调是"一次调用的上下文"，一次调用的上下文不应落到对象状态里（否则重启/重入时旧结果会投递给新回调）。

顺带一提 Qt 6 的小工具：`Qt::SingleShotConnection` 可以把一次性连接写得很干净——槽触发一次后自动断开，适合"等一次结果就完事"的场景：

```cpp
connect(worker, &Worker::done, this, [](const Result &r) {
    // 只触发一次，自动 disconnect
}, Qt::SingleShotConnection);
```

### 6.3 模式三：异步三件套

把上面的实践归纳一下，整套异步体系只有三件工具：

```
 ┌───────────────────────────────────────────────┐
 │ 异步三件套                                     │
 ├───────────────────────────────────────────────┤
 │ std::function 回调   ── 请求-响应的结果承载    │
 │ QMetaObject::invokeMethod ── 跨线程编组        │
 │ 信号与槽             ── 状态变化的一对多通知    │
 └───────────────────────────────────────────────┘
```

分工要点：

- **一次请求-响应用回调**，**状态变化广播用信号**。不要为单次请求新增 `xxxFinished` 信号——会导致信号爆炸，调用方还得自己配对请求和响应；
- 跨线程回主线程必须走元调用（`Qt::QueuedConnection`）或信号槽，**禁止直接跨线程调用 UI 或主线程对象**；
- 用 `invokeMethod` 时注意目标对象的线程亲和性——它决定槽函数在哪条线程执行。

### 6.4 模式四：生产者-消费者管线（例外场景）

"长任务用 QThread"有一个例外：**要求极致性能的多级流水线**——音视频 解码→渲染、采集→编码→推流 这类持续数据流。这类场景下生产者-消费者管线比"事件循环 + 异步回调"更快。

```
  采集/拉流      解码         编码/渲染      推流/上屏
 ┌────────┐ 队列┌────────┐ 队列┌────────┐ 队列┌────────┐
 │ 生产者  │───▶│ 消费者  │───▶│ 消费者  │───▶│ 消费者  │
 │std::thread│  │std::thread│  │std::thread│  │ 主线程  │
 └────────┘    └────────┘    └────────┘    └────────┘
   每一级独立线程，级间用阻塞队列衔接
```

**线程选型**：管线内部级线程是纯循环体、没有事件循环需求，可以用裸 `std::thread`——这是唯一的例外。与 Qt/UI 的交互仍收敛在管线两端的主线程包装对象上。**管线内部禁止触碰 QObject/UI**：帧数据用纯数据结构流转，出管线后才允许回主线程。

**级间队列**：默认选**有界阻塞队列**（定长环形缓冲 + mutex + condition_variable），队列满即阻塞，背压沿管线自然向上传导，内存可控。无界队列必须有书面理由（小包高频 + 输入天然限速 + 流控兜底）；**大体积数据（帧/图像）一律有界**。

**生命周期三件套**——管线正确退出的关键：

1. **abort 原子标志**：所有条件变量 wait 的唤醒条件必须包含 abort，禁止裸 wait；
2. **代际机制**（serial 序号）：seek/重置后丢弃跨代旧数据，不靠清空时序赌正确性；
3. **退出顺序固定**：`abort → notify_all → join`，禁止反序。

```
 退出流程：
  abort = true ─▶ cv.notify_all() ─▶ wait 醒来检查 abort
                                   ─▶ 循环退出 ─▶ join
   ★ 顺序不能反：先 join 没人唤醒，线程死等
```

### 6.5 能否阻塞的判别标准

一条线程上能不能写阻塞等待，只看一件事：**这条线程有没有事件循环**。

```
 该线程有事件循环？
  ├─ 有（主线程 / QThread Worker）→ 禁阻塞等待，用异步循环
  └─ 无（std::thread 管线级）     → cond.wait 阻塞即设计（背压）
```

**Worker 内禁止手写 `while` 阻塞循环**等待单次操作完成。迭代式任务（指令流、协议握手序列）要把循环展开为"可重入推进函数 + 完成回调续跑"，推进动力来自事件循环：

```
 阻塞 while（禁止）：
  事件循环 ──▶ run(){ while{ 读→同步发送→读→… } } ──▶ 处理 cancel
                        ▲
               cancel 元调用在此期间排队干等，取消"失灵"

 异步循环（正确）：循环的"栈"搬进成员
  事件循环 ─▶ run() ─▶ 空转 ─▶ run() ─▶ 空转 ─▶ run()
              块1 ▲          块2 ▲          块3
                  └─ cancel 在空转间隙被即时处理 ──┘
```

迭代的中间状态（如 next 索引）存成员变量而不存栈上，每步完成后让出事件循环，由完成回调重入续跑。

## 7. 小结

```
 本文要点回顾
  ├─ 版图：主线程×1（UI 专属）、子线程×N（长任务）、线程池（短任务）
  ├─ QThread：不重写 run()，用 Worker + moveToThread
  ├─ 通信：首选队列连接/元调用，锁是最后手段
  ├─ 选型：UI→主线程；常驻→专属 QThread；单发→线程池；
  │        流水线→生产者-消费者管线
  ├─ 模式：包装对象 + Worker + 异步接口 + 三件套
  └─ 红线：有事件循环的线程禁阻塞；跨线程禁直接 delete
```
